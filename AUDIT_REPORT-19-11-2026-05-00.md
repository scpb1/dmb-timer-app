## 1. Критические баги и потенциальные краши

### 1.1. SQLite: виджет может оставить приложение в режиме только чтения

| | |
| --- | --- |
| **Приоритет** | **High** |
| **Файлы** | `src/services/database/index.ts` — строки **54–59**, **82–106** |

**Суть:** Общий синглтон `database` / `openedFileName` используется и основным процессом, и Android widget handler. `openReadOnlyDatabase()` открывает соединение с `PRAGMA query_only = ON` (стр. 91–92). `openProfileDatabase()` при совпадении `openedFileName` **сразу выходит** (стр. 57–59), не пересоздавая writable-соединение.

**Сценарий:** виджет обновился в фоне до первого `initDatabase()` в UI → приложение стартует, считает БД уже открытой → записи (`setConfig`, дневник, трекеры) могут стабильно падать с ошибками SQLite.

**План исправления:**
1. Хранить метку режима соединения: `'read-only' | 'read-write'`.
2. В `openProfileDatabase` при `openedFileName === fileName` и режиме `read-only` — закрыть соединение и открыть заново без `query_only`.
3. Для виджета по возможности **не** подменять глобальный writer: отдельная переменная `widgetDatabase` или всегда `useNewConnection: true` без записи в общий `database`.
4. Добавить интеграционный тест/чеклист: «cold start после обновления виджета → запись в config».

### 1.2. Ошибка инициализации БД скрывается — UI запускается в «полусломанном» состоянии

| | |
| --- | --- |
| **Приоритет** | **High** |
| **Файлы** | `src/navigation/RootNavigator.tsx` — строки **35–56** |

**Суть:** В `bootstrap()` ошибка `initDatabase()` логируется (стр. 52–53), но в `finally` всегда выполняется `setBoot({ status: 'ready', ... })` (стр. 55). Пользователь попадает в онбординг/главную без работающей БД; последующие вызовы `getDatabase()` бросают `Error: База данных не инициализирована` (`index.ts` **147–150**).

**План исправления:**
1. Ввести состояние `boot.status: 'error'` с экраном «Не удалось открыть данные» и кнопкой «Повторить».
2. Не выставлять `ready`, пока `initDatabase()` не завершился успешно (или явный fallback только для web, если когда-либо появится).

### 1.3. Race: виджет vs основное приложение на одном `database` (без учёта режима)

| | |
| --- | --- |
| **Приоритет** | **High** (связано с 1.1) |
| **Файлы** | `src/services/database/index.ts` — **82–106**, **99–105**; `src/widgets/widgetTaskHandler.tsx` — **18–20** |

**Суть:** Между проверкой `if (database)` и присвоением (стр. 99–105) теоретически возможна гонка двух изолированных процессов (widget isolate / app). Даже без гонки совместное использование writer-connection виджетом и приложением обходит изоляцию `query_only`.

**План исправления:** разделить пулы соединений; для виджета — короткоживущее read-only соединение на время `loadHomeWidgetModels()` с гарантированным `closeAsync` в `finally`.

## 4. Безопасность и работа с данными

### 4.1. Дневник: PIN не шифрует SQLite и файлы на диске

| | |
| --- | --- |
| **Приоритет** | **High** (ожидания пользователя) |
| **Файлы** | `src/services/diaryLock.ts` — **55–60** (`DIARY_LOCK_DISCLOSURE`); БД — `src/services/database/diary.ts` |

**Суть:** Защита — уровень UI + SecureStore для секретов; при root/backup/доступе к каталогу приложения записи читаемы. Это честно раскрыто в UI, но остаётся системным риском.

**План исправления:** (долгосрок) SQLCipher / шифрование `content_json` с ключом из SecureStore; краткосрок — усилить тексты в онбординге замка, запрет backup в `AndroidManifest`/`Info.plist` где применимо.

### 4.2. Legacy-хэш PIN: SHA-256 без PBKDF2

| | |
| --- | --- |
| **Приоритет** | **Medium** |
| **Файлы** | `src/services/diaryLock.ts` — **109–111**, **130–146**, **139–146** |

**Суть:** Старые установки с `legacyHash` (SHA-256 от `salt:value`) слабее текущего PBKDF2 (`DIARY_KDF_ITERATIONS`). Миграция при успешном входе уже предусмотрена логикой `secretMatches`, но активные legacy-хэши остаются до следующего ввода PIN.

**План исправления:** принудительная миграция при разблокировке; баннер «обновите код» для legacy; снизить срок жизни legacy.

### 4.3. Экспорт книги писем: встраивание SVG как data URI без санитизации

| | |
| --- | --- |
| **Приоритет** | **Medium** |
| **Файлы** | `src/utils/exportLetterBook.ts` — **52–57**; `src/utils/letterBookHtml.ts` — **35–41**, **106** |

**Суть:** Текст экранируется (`escapeHtml` в `spanToHtml`), но SVG читается как строка и попадает в HTML/PDF. Вредоносный SVG теоретически может содержать script/foreignObject (зависит от PDF viewer).

**План исправления:** rasterize SVG в PNG (`expo-image-manipulator`); отказ от `image/svg+xml` в экспорте; whitelist MIME в `imageToDataUri`.

| **Файлы** | `bot/src/store.ts` — **73–78**, **169–178** |

**Суть:** Есть atomic rename (`tmp` → `store.json`), но два параллельных `patchChat` могут перетереть изменения (last-write-wins).

**План исправления:** очередь записи в процессе; file lock (`proper-lockfile`); или SQLite.

### 4.7. Валидация JSON config в БД: в основном на уровне parse с fallback

| | |
| --- | --- |
| **Приоритет** | **Low** |
| **Файлы** | `src/utils/timerRecords.ts` — **20–48**; `src/services/configJsonStore.ts` — **70–71** |

**Суть:** Повреждённый JSON в `config` обычно откатывается к defaults (хорошо для устойчивости), но **без уведомления пользователя** часть данных может тихо обнулиться.

**План исправления:** при `catch` в parse — флаг «восстановлено из резервной копии» + опциональный бэкап последнего raw в `config_backup_*`.
